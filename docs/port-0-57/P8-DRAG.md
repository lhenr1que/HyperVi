## 2. Bloqueio de K3/K9 (e do rearm)

API 0.57 do drag (`H:layout/supplementary/DragController.hpp`): além das operações `dragBegin`, `dragEnd`, `mouseMove`, `updateDragWindow` e `resetDragThresholdReached`, o público expõe só os observadores `target()`, `mode()`, `wasDraggingWindow()`, `dragThresholdReached()`, `draggingTiled()`, `exclusiveDeviceGrab()` e os sinais `m_events.{motion,ended}`; posição inicial, hotspot, contadores etc. são **privados**. Os observadores descrevem propriedades do drag, não a origem: uma sessão nova do usuário pode ter as mesmas. `endDragTarget()` devolve só "havia alvo". **Não há identificador de sessão.** A única invalidação por sessão é o sinal `ended`, que exige um ouvinte — o desenho de posse por sessão de P7 §5 (geração + `ended`), que pertence a Q4 (ouvinte com vida ligada ao unload, reentrada durante `dragEnd`).

Demonstração (host falso, `evidence/P8B-equiv.txt`, modo `blocker`): a barra inicia um drag na janela A; o host o encerra numa tecla (a flag `m_bDraggingThis` do plugin continua `true`, como hoje); um atalho do usuário inicia outro drag na **mesma** A; a barra solta o botão e tenta encerrar "o seu". Os três candidatos sem posse encerram o drag do usuário: (1) incondicional (semântica 0.56.2 de `changeMouseBindMode(INVALID)`), (2) `target() == alvo lembrado`, (3) `target() == alvo lembrado && mode() == MOVE` → **3/3 UNSAFE**. Rearm só com `begin`: com o próprio drag ativo, `begin` devolve `BEGIN_ALREADY_DRAGGING` e não reinicia. Logo K3, K9 e os dois rearm ficam como estão até Q4. Nenhum `endDragTarget()` foi introduzido (`hostDrag.hpp` não chama, a sonda B prova que não existe `KwDrag::end`).

**Dependência de Q4 identificada:** posse do drag por sessão (adquirida quando `begin` devolve `BEGIN_STARTED` e `target()` não é nulo; invalidada por `ended` com contador de geração), necessária para K3 (6 pontos), K9, os 2 rearm e para o passo 2 do unload. O retorno `eBeginResult` do helper já distingue "iniciou" dos três casos de recusa, para Q4 usar; hoje é ignorado nos chamadores, como o `SDispatchResult` antigo.

## 3. K1/K2: o que foi feito e o que muda

`plugin/hostDrag.hpp` (novo): `KwDrag::begin(eMouseBindMode)` = `O:managers/KeybindManager.cpp:949–968` (ramo `MODE != INVALID`) sobre as primitivas 0.57: sai se `dragController()->target()` existe (de qualquer um), `windowAt(cursor, RESERVED_EXTENTS | INPUT_EXTENTS | ALLOW_FLOATING)`, sem janela → sai, MOVE não-tela-cheia pergunta às decorações (`presentation().checkInputOnDecorations(INPUT_TYPE_DRAG_START, cursor)`), depois `beginDragTarget(layoutTarget(), MODE)` com os padrões (`forcedEdge = nullopt`, `exclusiveDeviceGrab = false`). Diferença deliberada: `MBIND_INVALID` (e qualquer outro modo) **não** encerra nada (`BEGIN_BAD_MODE`); nenhum chamador o usa. Sem estado, ouvinte, timer ou callback. O helper não mexe em foco; o `dragBegin` do host foca e eleva a janela arrastada (`rawWindowFocus` + `raise`), **igual** nas duas versões (`O:layout/supplementary/DragController.cpp:214–215`, `U:…:245–246`). Callbacks síncronos de decoração (`checkInputOnDecorations`) são código externo; o host falso não prova ausência de reentrada por eles (nenhuma regressão concreta demonstrada).

Diferenças do **host** ao iniciar (P7 §2; seguem RD condicionados à validação ao vivo): posição ao pegar janela ladrilhada/tela cheia (`MAPDRAGHOTSPOT`; `binds:drag_center_window` **não** tocado), limiar em coordenadas não transformadas, reset de `m_draggingTiled`, roteamento de *input capture*. K2 segue redimensionando a janela sob o cursor (herdado).
